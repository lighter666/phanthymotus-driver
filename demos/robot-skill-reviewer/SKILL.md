# Robot Skill Reviewer

审查机器人 Skill 是否值得沉淀为可复用能力。默认把提交材料视为待验证的设计，不因描述流畅、演示成功或名称新颖而降低标准。

## 审查目标

一个合格的机器人 Skill 应把语言模型的理解和规划转化为可执行、可感知、可调整、可恢复、可验证的人机协作闭环。它必须同时满足：

- **有真实能力增量**：核心价值不能只靠通用模型对话、推理或文本生成完成。
- **有明确特殊性**：解决边界清楚的任务，具有独特机制、专业流程或工具集成，而不是宽泛的“万能助手”。
- **有合理通用性**：能通过参数、环境感知或策略适配一类场景，而不是单人、单物体、固定坐标或一次性演示脚本。
- **有具身执行闭环**：覆盖触发、理解、必要确认、感知、行动、反馈、调整、验证和收尾。
- **安全且可控**：风险与授权、确认、中止、降级和人工接管机制相匹配。

## 审查方法

1. 先用不超过三句话还原 Skill 实际要帮助谁、在何种场景、依靠什么能力、达成什么可验证结果。忽略宣传性措辞。
2. 进行“模型原生能力排除测试”：假设移除传感器、执行器、外部工具、环境状态和持续交互机制；若核心目标仍可仅靠普通对话完成，判为模型原生能力包装。
3. 拆分能力来源：
   - 通用模型原生能力；
   - 机器人平台或外部工具已有能力；
   - 本 Skill 新增的流程、策略、状态管理、专业知识或集成机制。
4. 检查技能边界与差异化：目标是否清楚，支持和不支持范围是否明确，是否只是多个无关任务的集合。若未提供技能库目录，不得虚构重复项，应说明无法完成库内重复性核验。
5. 检查可复用性：指出可参数化部分、硬编码部分和合理支持边界，并验证能否举出至少三个同类但不同的应用场景。
6. 逐段检查交互与执行：触发 → 意图理解 → 前置条件 → 必要澄清/授权 → 环境感知 → 动作执行 → 过程反馈 → 动态调整 → 异常恢复 → 成功验证 → 结果反馈/状态复原。
7. 对模糊请求、环境不符、用户中途变更、依赖失效、执行未达标、安全风险、用户中止和多人冲突指令做压力测试。
8. 按 [审查标准与报告模板](references/review-rubric.md) 评分并作出唯一结论。

## 核心判断规则

### 不把模型原生能力包装成 Skill

普通问答、摘要、翻译、改写、分类、文本创作、计划生成、情绪陪伴或固定格式输出，本身不足以构成机器人 Skill。只有当任务引入真实环境感知、身体或设备控制、专用系统调用、跨步骤状态、现场反馈调整，或者人与机器人协作完成可验证的现实结果时，才可能具备准入价值。

不得仅因为提交包含长提示词、角色设定、复杂措辞或若干对话轮次，就认定它有能力增量。

### 平衡特殊性与通用性

理想形态是“目标明确、机制独特、参数可变”。过于宽泛的技能缺少边界；只适配固定用户、固定设备、固定房间、固定坐标或单次案例的技能则缺少复用价值。通用性不等于无限泛化，合理的前置条件和不支持范围应被明确保留。

### 流程必须自然且可执行

每个关键步骤都应能回答：谁执行、使用什么能力、操作什么对象、依赖什么输入、如何确认完成、失败后怎么办。将“智能处理”“酌情行动”“确保满意”“必要时调整”等没有判断依据的表述标记为不可执行。

机器人只在目标、权限或风险存在实质不确定性时提问；不得把交互写成僵硬问卷，也不得重复询问已知信息。高风险或不可逆动作必须在执行前获得适当授权。

### 成功必须可验证

“任务完成”“体验良好”或“用户满意”不是充分成功条件。优先要求来自环境状态、传感器结果、工具回执、对象位置、操作结果或用户明确验收的证据。不得在缺少证据时宣称成功。

## 信息不足时

先完成所有可以基于现有材料完成的审查，再把缺失内容列为证据缺口。不得替提交者虚构机器人能力、接口、权限、环境条件或成功证据。若缺失信息直接影响准入，结论不得为“通过”；通常判为“修改后通过”或“退回重构”，只有核心价值明显不成立时才“拒绝”。

## 结论约束

结论只能是：

- **通过**：价值明确、证据充分、流程闭环，可直接收录。
- **修改后通过**：方向成立，问题具体且可在不重做核心设计的情况下修复。
- **退回重构**：概念可能有价值，但技能边界、核心机制或执行闭环需要重新设计。
- **拒绝**：属于模型原生能力包装、缺乏独特价值、不可执行、过度一次性，或存在不可接受的风险。

评分不能抵消一票否决项。所有问题应按 P0/P1/P2 标注，并给出可验收的修改要求；避免只说“建议完善”。若结论不是“通过”，提供改进后的流程骨架，但不要替提交者虚构完整实现。

## 输出

使用 [审查标准与报告模板](references/review-rubric.md) 中的评分、压力测试和报告结构。保持结论直接、证据可追溯、修改要求可验证。若用户只要求简评，可压缩篇幅，但必须保留最终结论、能力增量判断、一票否决项、关键缺陷和下一步要求。
